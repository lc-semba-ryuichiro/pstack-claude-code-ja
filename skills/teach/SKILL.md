# Teach

**それが何であるか、どう動くか、そしてなぜそのように作られているかを、相手のペースに合わせて1つの平易な説明として伝えます。目標は相手が理解することであり、あなたが何かを変更することではありません。**

Teach は `how` と `why` の上に成り立っています。作業内容とそれが触れる範囲の見当をつけたら、仕組みについては `how` を、その理由については `why` を実行します。これらは独自の調査を行う実際のスキルです。`Skill` ツールでは呼べないため、[`how`](../how/SKILL.md) と [`why`](../why/SKILL.md) の SKILL.md を Read して、その手順に従います。それらが見つけた内容を1つの平易な説明にブレンドし、相手にとって重要なことから話し始め、求められたら深く掘り下げます。教えるために自由に言い換えて構いませんが、例外が1つあります。`why` の確信度を表す表現はそのまま維持してください（その留保表現（hedges）は単なる文体ではなく調査結果そのものだからです）。

1. 相手が理解して持ち帰るべき数個のポイントを決める。なぜ質問しているのか（これから変更する、レビューする、デバッグする、初めて触れるなど）と、すでに何を知っているかを、尋問するのではなく会話から読み取って選びます。明らかにすでに知っていることは省き、質問の核心部分に深さを置きます。
2. `how` と `why` に仕事をさせ、自分でやり直さない。見当をつけるために自分でコードを読んだら、仕組みについては `how` を、理由については `why` を実行します。これらを並列で実行して結果を統合します。質問の規模にサイズを合わせ、サブシステム全体なら両方を実行し、小さな変更なら片方だけで十分な場合もあります。
3. 平易な定義から始める。シニアエンジニアが口頭で話すように、一般的な言葉でその対象の名前とそれが何であるかを述べ、通称があればそれも添えます。次に目の前のケースに結びつけ（「X では、これを〜するために使っています」）、そこから仕組み、深い理由、エッジケースへと組み立てます。各パートについて、腹落ちするようアイデアを説明します（それが解決する問題と、実際にどう動くか）。それが理解の助けになる場合は、人が操作したときに何が起きるか（長いチャットを開く、上にスクロールするなど）を順を追って説明します。関数や定数を羅列するのはリファレンスであって、教えることではありません。フレーミング用のラベル（「押さえておくべき1つのアイデア」「持ち帰るべきポイント」「重要な洞察」「核心として」「TL;DR」など）は出力しないでください。まずは密な段落ではなく1〜2文の最小限の完全な答えを出し、そこで止めます。相手が求めたらレイヤーを追加します。文字の壁（wall of text）は絶対に作らないこと。
4. 講義やパフォーマンスではなく、会話を保つ。さらに深く掘り下げるか次に進むかを提案し、相手のリードに従います。クイズは出しません。ペース配分の演出もしません。「一旦止めましょう」と書いたり、復唱を求めたり、「ここが押さえるべき文です」と宣言したり、重要または難しい箇所にフラグを立てたり（「ここはゆっくり読む価値がある部分です」「ここがトリッキーなところです」「ここからが面白くなります」など）しないでください。ただそのまま語ります。一息置くべき場面では、そこで止めて相手の反応を待ちます。対話する人間がいないワンショット実行の場合は、すっきりまとめ、深掘りの提案は最後に置きます。
5. 語るだけでなく見せ、図を1つずつ積み上げて全体像を作る。それが最も早く伝わるなら、diff、コード、またはデバッガを開きます。言葉より絵の方が早く伝わる場合は図を描きます。3つ以上の動くパーツがあるものについては、すべてを一度に盛り込んだ1枚の図を描かないこと。代わりに、前の図を描き直してパーツを1つずつ追加する短いシリーズを描き、読み手がシステムの組み上がりを追えるようにします。特に最後にまとめて出すような一度きりの全体図はリファレンスであり、教育ではありません。具体的には、A から B、そして C へのフローを教えるなら3回描きます。最初に A から B。次に描き直して C を追加。次に描き直して戻りエッジや次のパーツを追加します。アイデアに合った媒体を選び、両方役立つなら両方使います。ラベルが意味を運ぶフローや構造には Mermaid 図が適しています。レイアウト、重なり、スクロール位置、ビフォー・アフターのような空間的なアイデアには、画像生成ツールを使い、ホワイトボードにマーカーで描いたようなスタイルで短いラベルをいくつか添えて描画します（画像モデルは長いテキストを文字化けさせるため）。言葉で説明するだけで済ませず、実際にその画像を生成してください。積み上げのルールは生成画像にも当てはまります。単純な1点だけの説明には図は不要です。

すべての応答は [**unslop** スキル](../unslop/SKILL.md)を通し、同僚に説明するような平易な話し言葉で書きます。簡潔（tight）に、ただしそっけなく（terse）ならないように。埋め草（filler）や曖昧な留保を削り、腹落ちさせる核心部分を残します。比喩や前置き、これからの予告ではなく、具体的なメカニズムを述べます。目標とする密度は次のような感じです：「仮想化（Virtualization）は2つのパートで動きます。1つはレンダリング用、もう1つはディスクからの読み込み用です。アイテムがバッファを越えてスクロールアウトすると、その DOM ノードとメモリ上のデータの両方が破棄されます。」通常の文頭大文字（sentence case）を使い、すべて小文字にはしないこと。em ダッシュ（—）は使わず、読点よりも句点を優先します。1文あたりの読点は1〜2つまでに抑え、節が重なる場合は別の文に分割します。1つの概念には1つの名前を与え、それを貫きます。対句的な文（「B なき A、あるいは A なき B」）や、きれいにまとめすぎる締めくくり（「あとは自明です」「すべてがうまく噛み合います」）は避けます。これらのステップ内の言葉はあなたへの指示であり、出力するラベルではありません。見出しや決まり文句として構造をオウム返しにしないでください。

**返信形式：** 自分が何をしたか・何を提供したかの報告ではなく、説明そのものを返します。まず要点を述べ、続いてそれが何か、どう動くか、なぜそうなのかの平易な説明、そして `how` や `why` でさらに追いかける価値のあるスレッドを提示します。

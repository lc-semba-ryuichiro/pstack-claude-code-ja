### Autopilot-full

**あなたが責任を持つのは最終判定（verdict）であり、個々の PR の実装そのものではありません。各 PR には専任のオーナーを1体割り当て、ビルドからマージまで一気通貫で担当させます。そして、そのコードを一文字も書いていない第三者の検証群（swarm）が、実際にマージされるコードの動作を証明するまでは、いかなる PR もマージさせません。**

1つの判定（verdict）が保証するのは1つのパッチ内容だけであり、グリーンの CI が保証するのは特定の1つのヘッドコミットだけです。ステップ 4 のフルスウォーム（総力検証）は基本1回だけ実行し、再実行するのは大きな仕様・構造変更が入った場合のみに限ります。`playbooks/shipping.md` に定められた patch-id ルールを使えば各検証レーンの結果を引き継げますが、新しいヘッドコミットが生成されるたびに、そのヘッド自身のグリーンな CI が別途必要になります。

1. **オペレーターの関門（ゲート）が最優先。** 承認（グラント）の効力が及ぶのはキューに登録されたアイテムのみです。オペレーターが「自分が担当する」と明言した項目や、キュー外の PR については、マージ準備完了（merge-ready）の状態で停止させてください。「計画を提示して」という指示は、実行開始の GO サインではありません。
2. **PR ごとに専任オーナーを1体起動し、後任がいつでも引き継げる場所に作業を残す。** 使用するフォージ（Git ホスティングツール）は、プログラム全体で最初に1回だけ判定して確定させます。デフォルトは GitHub CLI（`gh`）です。`command -v origin` が成功し、かつ Origin が対象リポジトリを解決できる場合は、すべての PR 操作に `origin pr` を使用してください。それ以外の場合は `gh` のまま進め、フォールバックした旨を記録に残します。Graphite（`gt`）を必須前提にしてはいけません。各オーナーは `isolation: "worktree"` で起動した独立したサブエージェントとして動作します。指示書には、最初にチェックアウトするトランクのブランチ名を書きます。オーナーは実装とビルドを行い、`playbooks/opening-a-pr.md` に従って PR を作成し、実際の成果物上で変更の動作を証明したうえで、`playbooks/babysit.md` に沿って CI がグリーンになるまで監視（babysit）し、ステップ 4 とステップ 5 をクリアした時点でマージを実行します。babysit プレイブックで「リベースを報告する」と指示されている箇所では、オーナー自身が自分のブランチをリベースし、`git push --force-with-lease` でリモートに反映してください。

   作業と並行して CI や自動ボットが走るよう、PR は早い段階でオープンしておきます。コードが「準備完了（code-ready）」とみなされるのは、AI 臭い冗長な記述の除去（`deslop` スキル。Cursor 向けの `cursor-team-kit` に同梱。使えない場合は SKILL.md の「絶対遵守事項」の通り平易な言葉で指示）と `/pstack:no-comments` のパスを通過した後だけです。これにより、フルスウォームが確実に完成状態のコードに対して実行されるようにします。その後、最新のトランク（trunk）ブランチ上にリベースし、自己証明（self-proof）を行う前に `code-ready` のヘッドコミットを報告してください。そうすることで、実際にパッチが着地するベース状態の上で検証が走るようになります。それ以降に新しいヘッドコミットが作られた場合も毎回報告し、自己証明・CI・監視（babysit）がすべて完了したら `merge-ready` を報告します。リベースするたびに CI が最初から再実行されてしまうため、修正ラウンド中はそのベースコミット上に留まって作業してください（ただし、トランクとコンフリクトする場合、トランク側の変更で CI が壊れる場合、または同じファイルに対する並行変更がトランクにマージされたことが判明している場合は例外としてリベースします）。`code-ready` のプッシュを行う前、およびその後の検証（verifier）を必要とするプッシュを行う前には、必ずコミット済みのヘッドに対して、変更したパスに関連するリポジトリ内のチェック一式を実行してください。

   オーナーはいつでも突然止まるものと仮定してください。起動したらすぐにブランチをプッシュし、[**show-me-your-work** スキル](../../show-me-your-work/SKILL.md)に従って意思決定ログ（decision trail）を開始します。ログの置き場所は、ルートエージェントが worktree の外にある絶対パスを決めて、各指示書に書きます。以降も、次の作業ユニットに着手する前に、完了したユニットを毎回プッシュしてください。サブエージェントを起動したエージェントは、親エージェントが死んだ場合でもルート側が状態を確認（プローブ）できるよう、そのサブエージェントの ID、ステータス、および過去の同種タスクの実行実績から算出した「スタック判定時間（stuck-after runtime）」を意思決定ログと同じ場所に記録します。フォースプッシュを行ってよいのは自分自身のブランチに対してのみとし、自分が最後にプッシュした（または引き継いだ）SHA に固定した `--force-with-lease` を必ず使用してください。自分が行ったものではない未知のプッシュを検知した場合は、即座に停止してルートエージェントに報告してください。
3. **各オーナーはスタック（積み上げ）ではなく、トランクから並列に走らせる。** これにより、各 PR が互いに依存せず単独でマージ（着地）できるようにします。
4. **スウォーム検証は原則1回だけ実行する。** フルスウォームは `code-ready` のヘッドコミットに対して1回だけ実行します。再度フルスウォームを回すのは、新しい振る舞いの追加、再設計、または大規模な新規差分が生じた場合のみです。単なるリベース、マージコンフリクトの解消、または軽微な修正であれば、新しいヘッドに対して検証役（verifier）を1体だけ割り当てます。文言のみの修正であれば検証役は不要です。[**swarm** スキル](../../swarm/SKILL.md)に従い、`code-ready` の SHA に対して独立した検証役を並列展開（ファンアウト）します。検証役は各種ゲートを再実行し、コントロールスキル（`control-ui` や `control-cli` など。使えない場合はブラウザ自動化ツールやターミナル）や指定のドライバーを使って実際のユーザー接点（サーフェス）上で核となる挙動をライブ実証し、さらに差分（diff）を監査します。ライブ検証レーンの完了なしに、あるいは `merge-ready` レポートに添付された証拠（レシート）をあなた自身が監査し終える前に、判定（verdict）をクリーン（合格）にしてはいけません。どの検証レーンも、自ら確認していない自己申告を信用しないのが鉄則です。

   PR をブロックしてよいのは、該当ヘッドコミットでの失敗した実行結果や、その PR によって誤りとなったドキュメントの行など、客観的に実証できる問題がある場合のみです。PR のベース側（トランクであれ、スタックの下位にある PR であれ）に元から存在していた問題は、今回の PR がそれをコピーしたか、新たにそのコードパスへ到達するようにした場合を除き、ブロック理由にはなりません。ブロック対象となるのは「ユーザーが実際に踏むバグ」「失敗したゲート」「出荷されるドキュメントの誤り」の3つだけであり、それ以外の指摘はすべてフォローアップタスクに回します。
5. **オーナーがマージしてよいのは、あなたが検証を完了し、かつ着地先のトランク上でテストされたコードだけ。** CI がグリーンになったという事実だけでは、決してマージの許可にはなりません。スウォームの各検証レーンが動き出したら、マージ準備（merge prep）として最新のトランク上にリベースし、新しいヘッドコミットを報告したうえで、CI がグリーンになるのを待ちます。

   トランクが動くたびに毎回リベースしていてはいつまで経っても終わらないため、マージの直前にトランクをフェッチし、「トランク側の変更がこのパッチに影響を与え得るか」を判定してください。コンフリクトが発生した場合、双方で同じファイルが変更された場合、あるいは PR に対して実行されるチェック内容自体が変更された場合など、「マージ後に着地する状態のコードが一度もテストされていない」状況では、リベースして CI の完了を待ちます。ロックファイルが双方で変更された場合でも、マージ結果に対してロックファイル固定のインストール（frozen install）が成功し、かつこの PR が変更するパッケージ群がヘッドコミット上と同じバージョンに解決されるなら、リベースは不要です（そのインストール自体が実際に着地するロックファイルのテストになるためです。逆にインストールが失敗した場合は、リベースしてロックファイルを修復する必要があります）。トランク側で「このパッチの呼び出し元」や「このパッチが依存している対象（呼び出し先のコードや依存パッケージのバージョンなど）」が変更されている場合は、マージ結果に対してこのパッチのチェック一式を実行し、パスすればマージします。それ以外の場合はそのままマージしてください。マージ準備（merge prep）の段階を過ぎてからトランクの動きによって3回目のリベースが必要になった場合は、処理を保留してルートエージェントに報告し、競合する作業の実行順序をルート側で交通整理させます。
6. **ルートレイヤーの運用を徹底する。** 予算上限の引き上げや許可リスト（allowlist）への追加など、関門（ゲート）の基準を緩める変更には、必ず検証役（verifier）による妥当性の証明と、その後にあなた（ルート）が発行する新しい副署（countersign）が必要です。オーナー自身は「早くグリーンにしたい」というインセンティブを持っているため、自己判断で緩めさせてはいけません。承認権限を含むグラントのもとでは、この副署が正式な承認となり、オーナー側の記録にも検証レーンが照合できるようあなたの副署への参照を残します。チェック自体の無効化やソフトフェイル（失敗してもパス扱いとする設定）は、あらゆるケースに対する防御機能を失わせるため、例外なく取り除いてください。また、フォージ（GitHub など）側でシステム的に強制されている承認フローを勝手に代行したりバイパスしたりすることは絶対に厳禁です（ルートによる副署はフォージ側の承認権限の代わりにはなりません）。

   オペレーターから開始の GO サインが出たら、長時間の実行によるズレ（ドリフト）やエージェントのサイレントな停止を防ぐため、委譲された作業がすべてなくなるまで `/loop 1h` をセットして定期監査を回します。各ティック（定期実行タイミング）では、トランクからこのプレイブックを読み直したうえで、未報告のヘッドコミットや未記録のサブエージェントといった記録上のズレ（ドリフト）を検知し、担当オーナーに記録させて修正します（ドリフトはエージェントの停止ではなく、あくまで記録の抜け漏れです）。さらに、末端の検証レーンに至るまですべてのエージェントをプローブし、ステータスの文面や要約報告ではなく実際の副作用（コミット、ログ追記、成果物など）を基準に状態を判定します（要約テキストの裏で子エージェントがスタックしているケースを見逃さないためです）。エラーを吐いている場合、新しいターンを開始できない場合、または「スタック判定時間（stuck-after runtime）」を過ぎても新しい進捗が一切見られない場合、そのエージェントはスタックしているとみなします。最初のティックまでに一度もプッシュせず意思決定ログも1行も書いていないオーナーも同様にスタック扱いです。ただし、あなた（ルート）やオペレーターからの返答を待っている状態はスタックではないので、適切に回答して進めてください。スタックしたエージェントは、停止処理の完了を待たずに即座に新しいエージェントへ置き換えます。そのティックの間にオペレーターにとって意味のある変化が起きた場合は、最後に [**ketchup** スキル](../../ketchup/SKILL.md)で状況をキャッチアップして報告し、何も変化がなかった場合は静かに待機を続けます。
7. **オペレーターから停止指示が出たら即座に待機（スタンドダウン）する。** 保留（ホールド）の指示は「一切の書き込み禁止（zero-writes）」の命令としてすべてのオーナーに伝達されます。各オーナーは現在の進捗状況を報告し、オペレーターが解除するまで現在の任務内容（ブリーフ）を保持したまま待機します。

**返信形式：** [**ketchup** スキル](../../ketchup/SKILL.md)に従ってオペレーターに最新状況を報告してください。各 PR の状態と判定（verdict）、マージ済みの項目、発行した副署（countersign）とその理由、オペレーターの判断待ちとなっている関門（ゲート）、および保留中のフォローアップタスクを網羅し、各 PR と意思決定ログ（trail）へのリンクを必ず添えてください。

### Autonomous run

**終了条件（exit condition）の責任者はあなた自身です。「完了の定義」を明確に定めたら、そこに到達するまで止まらずに突き進んでください。**

1. 最初のイテレーションに入る前に、終了条件を客観的に判定可能な述語（テストがすべてパスする、再現バグが修正される、全 N 件の PR がマージされる、ピクセル差分がゼロになる、など）として明言します。
2. Claude Code 組み込みの `/loop`（pstack のスキルではありません。`/loop 5m <prompt>` の形で使い、間隔を省くと自分でペースを決めます）を使って、再起動（ウェイク）の仕組みを選択します。監視すべき特定のイベント（CI の完了、マージ、Git ref の更新など）がある場合は、イベント発生時にあなたを起こすウォッチャー（監視役）サブエージェントを配置し、フォールバックとして長めの間隔の定期ハートビートを設定します。監視すべきイベントがない場合は、「結果が再チェックに値するタイミング」に合わせた固定間隔のハートビートを設定してください。各サブエージェントの推論レベルは、Subagents セクションの基準に従ってタスクの性質に合わせて選択します。
3. 各イテレーションでは、根拠（エビデンス）によって正当化される最小限の変更だけを加え、終了条件（述語）に対して検証し、前進していればコミットし、役に立たなかった変更は即座に破棄します。「念のために入れておけば助けになるかも」といった二重保険的なコードは、そのまま残さず必ずリバートしてください。
   作業の順序立てには [**sequence-verifiable-units** 原則スキル](../../principle-sequence-verifiable-units/SKILL.md)を適用し、最後にまとめてチェックするのではなく、1つの作業ユニットを検証し終えてから次のユニットに着手します。
4. 実行の途中で見つかった「ゴールの達成を支える課題」は、すべてあなた自身が引き受けて対処してください。壊れたスキル、関連するバグ、不安定（フレーキー）な検証ツール、レビューのノイズ、ツーリングの不具合、放置されたフォローアップ項目、修正可能なズレ（ドリフト）などは、poteto-mode を使って自力で解決します。本来のスコープ外（アウトオブバンド）の修正は、専用の別 PR に切り出してまとめてください。後から取り消せる（可逆な）作業を人間待ちとして保留したり、`AskUserQuestion` を使ったりしてはいけません。人間に判断を仰ぐのは、取り消しの効かない不可逆な操作、どんな実験を行っても決着がつかない純粋なプロダクト方針・好みの判断、あるいは本当にどうしようもない手詰まり（デッドエンド）に陥った場合のみに限ります。あくまで終了条件（述語）の達成を主軸に据え、脇道の修正が終わったら必ず本筋のループに戻ってください。
5. イテレーションごとに [**show-me-your-work** スキル](../../show-me-your-work/SKILL.md)でチェックポイントを記録し、「何を変更したか」と「終了条件に向けて前進したか」を1行ずつ書き残します。
6. 終了条件を満たしたら停止します。進捗が停滞（プラトー）しているだけでは停止の理由になりません。アプローチを切り替えて停滞を突破し、前進を続けてください。ただし、同じ場所を空転し続けるのではなく、本当の手詰まり（デッドエンド）に達したときは正直にエスカレーションしてください。また、勝利宣言をするために終了条件の基準を勝手に緩めることは絶対に厳禁です。

**返信形式：** 終了条件、実行したイテレーション回数、採用（マージ／コミット）された変更、破棄された変更、および終了条件の最終的な判定結果を報告してください。

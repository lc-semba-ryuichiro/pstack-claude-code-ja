# 自分好みにカスタマイズする

`poteto-mode` はあくまで一人の開発者のスタイルに過ぎません。その裏側にあるプレイブック、ルーティング、モデル役割分担といった仕組みは、あなたのスタイルにもまったく同じように機能します。このページでは、自分専用のモードの生成、セッションから得た教訓の定着、エージェントが同じミスを繰り返さないためのリポジトリ側の改善、特定の目的に特化したスキルの作成、そしてスキル変更を信頼して採用する前のブラインドテストについて解説します。

思っているよりも小さく始めてください。初日からたくさんのスキルを揃える必要はありませんし、このプラグイン全体を使いこなす必要すらありません。まずは普段通りにプロンプトを打ち、エージェントがどこでつまずくかを観察し、同じ失敗が2回起きたときに初めてスキルやチェック機構を追加すれば十分です。

## `/pstack:automate-me` で自分専用のモードを生成する

```text
/pstack:automate-me
```

自分のスタイルを言葉で説明する必要はありません。[`/pstack:automate-me`](../../skills/automate-me/SKILL.md) があなたの履歴から直接それを読み取ってくれるからです。現在のワークスペースにおける直近のトランスクリプト（対話履歴）をマイニングし、返信のトーン、タスクの委譲方法、検証の進め方、コードや文章の好み、開発プロセスなどにおいて繰り返し現れる傾向を抽出したうえで、どのパターンが本当に「あなたらしい」かを質問してきます。その後、Agent Skills 形式（`name` と `description` の YAML フロントマター付き `SKILL.md`）で `.claude/skills/<あなたの名前>-mode/SKILL.md` のドラフトを作成し、[`/pstack:unslop`](../../skills/unslop/SKILL.md) で文章を整えたうえで、通常のコード変更と同じようにレビューできるよう worktree から PR を作成します。

自分の作業スタイルや習慣が変わってきたときは、いつでも再実行してください：

```text
/pstack:automate-me 前回の編集以降に蓄積されたすべての履歴をもとに、自分のモードスキルを更新して
```

更新モードでは、スキルが最後に変更された時点以降の履歴だけをマイニングします。矛盾していないルールはそのまま維持し、新しい根拠が見つかったルールは改訂し、新しいパターンに対してのみセクションを追加します。

## `/pstack:reflect` でセッションの教訓を記録する

何か新しい学びがあったタスクの直後に、次を実行してください：

```text
/pstack:reflect 今回は時間がかかりすぎた。次回同じことを繰り返さないように、今回学んだ教訓をスキルに落とし込んで。
```

[`/pstack:reflect`](../../skills/reflect/SKILL.md) はトランスクリプトを読み込み、将来のエージェントの作業を変える価値のある教訓だけを抽出し、提案を `Accepted`（採用）、`Rejected`（却下）、`Backlog`（保留）に分類します。スキルの変更を適用する前には、必ずあなたの承認を待ちます。将来の意思決定を実際に変えるものだけを承認してください。たった1回の特殊なセッションは単なる逸話（レアケース）であって、ルールにすべきものではありません。

## `/pstack:correct` で開発環境（リポジトリ側）を修正する

エージェントの同じミスを何度も繰り返し修正しているなら、直す場所は次のプロンプトではなくリポジトリそのものです。対策は以下の有効性が高い順にランク付けされます：

1. アーキテクチャやより優れたデータ構造によって、そのミス自体を構造的に不可能にする。
2. 型システム、または「修正方法をエラーメッセージで明示する Lint や CI チェック」によってブロックする。
3. テストによって検知する。
4. ドキュメントやエージェント向けルールとして書き残す。エージェントがルールを読み飛ばしても何もエラーにならず失敗しないため、これは最後の手段になります。

このリストに「人間によるレビュー」は入っていません。すべての PR で同じミスを人間が毎回見つけなければならない状態こそが、この仕組みで解決すべき問題だからです。[`/pstack:correct`](../../skills/correct/SKILL.md) がその作業を代行します：

```text
/pstack:correct エージェントがリポジトリ層を経由せず、データベースクライアントを直接呼び出し続けてしまう
```

このスキルは直近のコミット、リバート履歴、レビューコメント、および場当たり的なワークアラウンドを説明するコメントを読み込み、ミスをパターン（クラス）ごとにグループ化します。同じミスが2回発生すると1つのクラスとしてカウントされます。最も頻度の高いクラスから順に、機能する最も高いレイヤーで1コミットずつ修正を行い、新しく追加したチェックが過去の実際のミスで確実に失敗することを証明します。また、エージェント指示ファイル内に「各ルールとそれを強制する仕組み」を対応付けた表を維持するため、何の強制力も持たない形だけのルールは再発時にすぐ浮き彫りになります。返信には、各クラスの根拠、選択した対策レイヤー、そしてなぜそれより高いレイヤーを使えなかったのかが記載されます。

引数を指定せずに実行すると、履歴から独自にミスのパターンを洗い出します。`/pstack:reflect` と `/pstack:correct` は役割を分担しています。`/pstack:reflect` は1つのセッションからスキルを改善し、`/pstack:correct` は同じ種類のミスが二度と起きないようにリポジトリ側を変更します。新しい境界を設けるような修正の場合は `/pstack:architect` と組み合わせてください。[1つのタスクではなく、作業キューを一晩でさばく場合](./07-overnight.md#1つのタスクではなく作業キューを一晩でさばく場合) には、リポジトリ全体に対してこの両方を実行するプロンプト例が載っています。

## 特定の目的に特化したスキルを作成する

定着させたいワークフローがすでに明確な場合は、次のように依頼します：

```text
/pstack:poteto-mode このリポジトリでデータベースのマイグレーションを検証するためのスキルを書いて
```

スキルの新規作成は [Authoring or modifying a skill プレイブック](../../skills/poteto-mode/playbooks/authoring-a-skill.md) にマッチングされ、Agent Skills 形式の `SKILL.md` を直接書き、フロントマター（`name` と `description`）やリンクの妥当性を検証したうえで、Opening a PR プレイブックを通じて成果物を PR 化します。エージェント向けの文章には人間向けの文章よりも高い基準が求められます。なぜなら、役に立たない曖昧な1文が、将来のエージェントが従う指示になってしまうからです。フリーハンドで `SKILL.md` を書くのではなく、プレイブックにその品質基準を維持させましょう。

なお、2つの特殊なケースには専用のジェネレーターが用意されています。アプリを実際に操作して挙動を証明するスキルは「検証スキル」なので、代わりに [`/pstack:create-verification-skill`](../../skills/create-verification-skill/SKILL.md) と [`/pstack:maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md) を使用してください。モデルチェッカーや数学的証明、その他の検証器を使ってコードの性質をチェックするスキルは「形式検証スキル」なので、[`/pstack:create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md) と [`/pstack:maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md) を使用します。どちらも [結果を検証し、PR を作成する](./06-verify-and-ship.md#形式検証スキルでコードの性質を証明する) で詳しく解説しています。

## `/pstack:technical-writing` で一定の基準を満たすドキュメントを書く

リリースする文章はスキルだけではありません。ドキュメント、RFC、README、PR 説明文、コミットメッセージには次を使います：

```text
/pstack:technical-writing README の変更箇所をレビューして
```

[`/pstack:technical-writing`](../../skills/technical-writing/SKILL.md) は重層的なドキュメント基準を適用します。目指すのは、疲れ切ったエンジニアでも一読しただけで理解できる文章です。まずドキュメントのモード（チュートリアル、ハウツー、リファレンス、または解説）を選択し、次に1文ずつ精査します。「誰が何をするのか」を明確にし、1文に1つの思考だけを込め、二通りの意味に解釈できる表現を排除します。あなたやエージェントが書いたばかりの文章をレビューするために使うことも、ドキュメント作成を依頼する最初から名前を指定しておくこともできます。

## スキルの変更をブラインドテストする

スキルの編集は将来のすべてのセッションに影響を与えるため、実験と同じようにテストしてください。他の人のスキルを取り入れる場合も同様です。本格的に採用する前に、自分の作業においてエージェントのパフォーマンスが本当に向上するかを確かめましょう。

```text
/pstack:poteto-mode このスキル変更に対して eval プレイブックを実行して。両方のバリエーションに同じタスクを与え、候補側は何も知らされないブラインドの状態に保って。
```

スキルが何度も見落としをしていて、本来どう動くべきかが分かっている場合は、変更とテストを1つのタスクでまとめて行います：

```text
/pstack:poteto-mode マイグレーションの漏れを指摘するようにレビュースキルを更新し、その変更を eval で評価して。
```

最初から eval（評価）を要求しておくことで、編集の妥当性が保たれます。1回の失敗セッションだけをもとに書かれた修正はそのセッションに過剰適合（オーバーフィット）しがちで、編集を重ねるうちにスキル本来の目的からズレていきます。eval を使えば、リリース前にそのズレを検知できます。

[Eval プレイブック](../../skills/poteto-mode/playbooks/eval.md) は、1つの失敗モード、すなわち「観察者効果（observer effect）」を防ぐことを中心に設計されています。評価されていると気づいたエージェントは普段と違う振る舞いをしてしまうからです。そのため、候補エージェントにはサニタイズされたディレクトリ内で自然なタスクを与え、「eval」や「候補（candidate）」といった言葉や、他の候補の存在を一切知らせません。1人の審査員（judge）が中立的なラベルのもとですべての出力を採点し、参照の連鎖をたどったか（chain-following）はエージェントの自己申告ではなく「実際にどのファイルを読み込んだか」に基づいて採点されます。

判定結果（verdict）を受け入れる前に、すべての出力にあなた自身で目を通してください。もし審査員の判定に納得がいかない場合は、自分の判断を疑う前に、まず評価基準（ルーブリック）のほうを疑ってください。

**落とし穴（Pitfall）：** スキルの挙動がおかしいからといって、タスクの途中でスキルを編集しないでください。スキルの修正は独立した別の PR で行い、元のタスクはそのまま進めましょう。機能開発の作業に絡み合った状態で出荷されたスキル変更は、レビューで見落とされ、評価することも不可能になります。

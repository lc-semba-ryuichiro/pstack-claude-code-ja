# 検証スキルをメンテナンスする

Claude Code で使用する場合は、このスキルに従う前にセッションごとに1回 [Claude Code アダプター](../../docs/harness/claude-code.md) を読み込んでください。pstack スキル内の Cursor 固有の名称を Claude Code 用にマッピングします。

機能マップは、アプリに変更が加わった瞬間から陳腐化（腐敗）し始めます。このスキルは、`/create-verification-skill` によって生成されたスキル（または機能マップを備えたあらゆるプロジェクト固有の検証スキル）を最新状態に保つためのメンテナンスループです。ここでの厳格さ（リガー）の単位は「1文ごと」ではなく「機能（フィーチャー）ごと」です。すべての箇条書きを逐一コマンド化しようとせず、すべての機能ファイルをソースコードから裏取りし、すべての機能を実環境（ライブ）で操作してカバーしてください。

## 判定結果（Outcomes）

以下のいずれか1つを選び、結果を明言してください：

- **clean（問題なし）：** すべての機能についてソースコードとライブ実行の両面でカバーが完了し、修正してリリースすべき変更が何もない状態。ブランチも PR も作成しません。
- **changed（更新あり）：** 実証済みのドキュメント修正、ハーネス修正、または機能マップの更新を1つの PR にまとめてリリースする状態。
- **blocked（ブロック）：** カバレッジの完了まで辿り着けなかった、または実証済みの修正を安全にリリースできなかった状態。何がブロッカーになったのかを具体的に明記してください。

## 編集スコープ

編集してよいのは、検証スキル自身のディレクトリ配下（`SKILL.md`、`features/`、およびそのスキルが所有するハーネススクリプト）のみです。実行中にプロダクトコードには決して手を触れないでください。機能マップに書かれている挙動をアプリがしなくなっている場合、それは「ドキュメントのドリフト（マップを直す）」か「プロダクトのリグレッション（バグとして報告する）」のどちらかです。ドキュメント側を書き換えてプロダクトの不具合をもみ消すようなことは絶対にしてはいけません。

## メンテナンス手順

0. **対象スキルを特定する（Locate the target）。** メンテナンス対象となる検証スキルを探します。本文に起動（launch）や操作（drive）のセクションがあり、機能マップを備えているプロジェクト固有スキル（通常は `.cursor/skills/verify-*/`）が対象です。候補が複数見つかった場合はどれを対象にするかユーザーに確認し、1つも見つからない場合は勝手に対象を捏造せず処理を停止して `/create-verification-skill` の使用を案内してください。

1. **インデックスの整理（Index hygiene）。** 機能マップの README を読み込み、同じディレクトリ内のファイルを glob で一覧取得します。記載漏れ、余分なエントリ、重複、リンク切れを修正してください。ここは軽量なチェックに留め、大げさな一覧表を自動生成する必要はありません。

2. **ソースコード調査ウェーブ（Source wave）。** 機能ファイル1つにつき1体の読み取り専用（read-only）サブエージェントを割り当て、並列で起動します。各サブエージェントはソースコードを読み込み、「このユーザー向け機能はどう動くのか？」を解説したうえで、ドキュメントのドリフトが疑われる箇所を根拠のコード位置付きで指摘し、簡潔なライブ検証レシピを1つ返します。子エージェントは絶対にアプリを操作したりファイルを編集したりしてはいけません。返却フォーマットは「機能の概要 / ソースコード上のエントリーポイント / ドリフトの可能性（またはなし） / 検証レシピ1本」とします。

3. **突合と整理（Reconcile）。** すべての機能ファイルについて要約が揃ったら、重複する検証レシピを統合し、検証に必要なアプリの状態遷移が最小限で済むようにまとめます。ドリフトの指摘があった箇所はスポットチェックで裏取りし、問題なし（clean）と報告された箇所を再度証明し直さないでください。また、直近の変更履歴（churn）をざっと確認し、機能マップから抜け落ちているユーザー向け機能（サーフェス）がないか探します。ただし、何かを「記載漏れ」と断定するには、必ずソースコード上の具体的なパスを根拠として提示してください。

4. **実環境パス（Live pass）。** ソースコード上では問題なさそうに見えても、実環境での動作確認は必須です。アプリ操作はすべてコーディネーター（親エージェント）自身が行い、対象となる検証スキル自身の起動モデルに従ってください。サーバーや UI であれば長寿命の1インスタンスを起動して直列に操作し、短命な CLI であれば操作ごとに新しい隔離セッションを立ち上げます（どちらに従うかは、このスキルではなく対象スキルの Launch セクションの記述が決めます）。すべての機能を最低1回は実際に操作し、途中でどのような失敗が起きても、プロセス全体を通じて以下の3つの不変条件を必ず守り抜いてください：
   1. **直前に予期せぬ挙動を起こしたインスタンスは、ヘルスチェック（doctor）を通すまで絶対に操作しない。** 最初の操作の前、セッション単位で動く場合の新しいセッション開始時、そして操作が失敗した直後には必ず `doctor` を実行してください。`doctor` では検知できない不具合（プロセス自体は生きているが UI の状態が固まっている場合など）では、奇跡を願って続行するのではなく、既知のクリーンな状態へリセットするか再起動してください。
   2. **それまでに取得した証拠は、あらゆるクリーンアップ処理後も生き残っていなければならない。** 推測で済ませず、指定された保存場所にファイルが実在することを必ず目で確認してください。
   3. **ある操作のために起動したものは、その用途が終わった時点で確実に片付ける。** セッションがハングした場合でも、終了した場合でも、共有インスタンスを使っている場合でも、失敗したイテレーションの残骸（ゴミ）は必ず掃除してください（共有インスタンスの場合はインスタンス自体を殺すのではなく、残したゴミデータだけをクリーンアップします）。
   スキルの記述が古くなった（ドリフトした）せいで `doctor` が失敗した場合は、ドリフトとして扱います。編集スコープ内でスキルを修正し、修正によって無効になった部分だけを再起動して（それ以上余計な再起動はしないこと）、1回だけリトライしてから、それでもダメなら `blocked` と判定してください。到達できない機能を `verified-unreachable`（到達不能と確認済み）と記録してよいのは、到達を妨げている具体的な前提条件（認証・権限・OS・外部状態など）と、試行したルートを明記できる場合に限ります。機能マップ側にその前提条件の記載が抜けていた場合は、それもドリフトです。トリアージの結果ハーネスを修正した場合は、PR に含める前に必ずライブ環境で再実行して動作を証明してください。最終的なティアダウン（終了処理）は、それらの再証明を含むその実行の最後の操作が終わった後に行い、何も残らないようにします（ただし証拠アーティファクトはスキルの規定通り残します）。

5. **トリアージ（Triage）。** ユーザー視点の説明が間違っている、または抜けている場合は「ドキュメントのドリフト（doc drift）」なので修正します。アプリ自体は正しく動いているのにハーネス側で操作できない場合は「ハーネスの不備（harness gap）」なので修正します（ハーネスの修正でも生成時と同じヘルパー規約に従い、スクリプトを実行可能にしたうえでスキル本文に呼び出し方を明記してください）。アプリ自体の挙動が実際に壊れている場合は「プロダクト側の不具合（product gap）」です。ユーザーへの報告用に記録は残しますが、今回の PR には含めないでください。

6. **出荷または停止（Ship or stop）。** `changed` の場合は、修正したすべてのファイルを事前に読み直したうえで、実証済みの修正だけをまとめた PR を1つ作成します。`clean` または `blocked` の場合は PR を作成せず、判定結果とカバレッジの状況を正直に報告して終了します。

実行中の簡潔な作業メモ（カバーした機能、到達不能だった前提条件、確認されたドリフト、最終判定など）は一時的なスクラッチ領域に記録し、リポジトリにはコミットしないでください。

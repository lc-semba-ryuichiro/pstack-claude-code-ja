# Recall

Claude Code では、このスキルに従う前にセッションごとに一度 [the Claude Code adapter](../../docs/harness/claude-code.md) を読んでください。ここには pstack スキル内の Cursor の名前と Claude Code のマッピングが記載されています。

**作業を開始または再開する前に、ユーザーの直近の作業コンテキストを再構築し、現在の状況と次に行うべきことの簡潔な要約（カプセル）を返します。**

簡潔に、トピックから逸れないようにすること。スコープ内のスレッドが必要とするものだけを読み、そこで止めます。

コンテキストは2つの記録に存在します。あなたのチャット履歴には、あなたが行ったことと決定したことが保持されています。共有の記録には、同じコード周辺で別の名前の下に起きたすべてのこと（ユーザーが報告し続けている症状、リリースされた後にリバートされた修正、本番環境で発生し続けているエラーなど）が保持されています。この2つ目の記録は、ソース管理、課題トラッカー（issue tracker）、チャットや課題のチャンネル、長文のドキュメント、およびエラートラッキングに存在します。バグの尾を引く機能のストーリーの大部分はそこにあるため、自分のトランスクリプト（会話ログ）だけで再構築してはいけません。

トランスクリプトは `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl` に保存されています。`<slug>` は、ワークスペースのパスから先頭のスラッシュを除き、各 "/" を "-" に置き換えたものです（例: `/Users/you/proj` は `Users-you-proj` になります）。各行が1つのチャットメッセージです。

1. **分類し、ルーティングする。** 再開すべき特定の過去のチャットが1つだけなら、それは `session-pickup` プレイブックの対象であり、これではありません。習慣を永続的なスキルに変えるのは `automate-me` の役割です。作業の人間向けの要約を作成するのは別のタスクです。Recall は、アクションを起こす前に最近のチャット群から作業コンテキストをロードするものです。ユーザーがすでに完全な状態カプセル（パス、ブランチ、変更内容）を提供している場合は、それを使用し、マイニング（発掘）はスキップします。
2. **検索前にスコープをロックする。** ウィンドウ（「最近」は実際の範囲であり、デフォルトは過去7日間）、トピック（指定されている場合）、およびワークスペース（デフォルトはアクティブなもの。要求されない限り、他のプロジェクトのトランスクリプトは絶対に読まないこと）を固定します。スコープを復唱（state back）します。無断で「すべて」を「最近のN件」に変更してはいけません。
3. **チャット履歴全体にファンアウト（fan-out）する。** 高速で安価なモデルを使って並行サブエージェントを生成し、それぞれにコーパスの一部を割り当てます。すべてのサブエージェントに対し、候補を UUID の名前ではなく実際の更新日時（`ls -t`）で並べ替え、まずトピックで grep し、一致したチャットの関連する領域のみを読み、現在のチャットと明らかなノイズ（サブエージェント、eval、およびテストチャット）はスキップするように指示します。各エージェントは同じスキーマで、チャットごとに1つのブロックを返します。内容は、トピック、ユーザーの目標、決定事項、未解決のスレッド、苦戦した点と修正、および成果物（PR、チケット、ブランチ）であり、それぞれにチャット UUID を引用します。チャットが1〜2個の場合は、ファンアウトをスキップして直接検索します。生のトランスクリプトはサブエージェント内に留め、メインスレッドには彼らの調査結果のみを渡します。ジョブに応じた各サブエージェントの推論レベルは、**poteto-mode** スキルの Subagents セクションに従って選択します。
4. **トピックが機能、ファイル、サブシステム、領域、またはバグの名前である場合は、共有の記録をスイープ（掃引）する。** これはデフォルトであり、判断の余地はありません。「私の X に関する作業」であっても免除されません。情報源ごとに1つの調査サブエージェントをエージェントモードで生成します（readonly にすると MCP へのアクセスが剥奪されるため）。そして各エージェントに「現在の状態はどうか、何が試されて定着しなかったか、ユーザーはまだ何を報告しているか」を尋ねます。これらをチャット履歴のマイニングと並行して実行します。結果が null であることも1つの発見です。利用できない MCP はスキップし、その旨を伝えます。戻ってきた結果を要約（brief）に組み込みます。このステップをスキップしてよいのは、名前付きのターゲットがない純粋なアクティビティの思い出し（「今週何をしたか」など）の場合のみであり、その場合は自分自身の履歴と現在の状態が答えのすべてになります。
5. **現在の状態と照合する。** マイニングとスイープで浮上した PR、ブランチ、チケットを取得し、`git` と `gh` を使ってチェックします。エージェントが実際に何をしたか（実行したツール、読んだファイル、直面したエラー）が答えの鍵となる場合は、ローカルのトリミングされたコピーではなく、トランスクリプトの全文を読みます。
6. **以下の契約（contract）に従って要約を書く。** スレッドごとにグループ化します。指定されたトピックから逸れないようにします。

## 出力の形式（Output contract）

最初にカプセル（要約）、次にスレッドのステータス、次に問題点、最後に次の行動（next move）を書きます。より深い詳細はその下に置くか、カットします。

- **Capsule.** 最大5つの箇条書き。この作業が何であり、全体としてどのような状況にあるか。
- **Threads.** 1行に1つずつ、必ず1つのステータスタグを先頭に付けます。`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、または `[planned, not started]` のいずれかです。タグのないスレッドはまだ完了していないため、タグを付けます。
- **Problems.** 最大5つまで、繰り返し発生しているものを挙げます。ユーザーが報告し続けている症状や、リリースされた後にリバートされた修正を含め、次の試行が前回の失敗箇所からスタートできるようにします。
- **Next move.** 最も有用な次の1手（具体的であること）。

隣接する機能やチケットは、それがこの作業をブロックしていない限り除外します。カプセルとスレッドの行が1画面に収まらなくなった場合は、スレッドをカットする前に詳細をカットします。要約は **unslop** スキルを通して書き、チャットでの発見は UUID で、共有記録での発見はそのソース（PR番号、チケットID、チャットのパーマリンク、エラートラッカーの issue）で引用します。また、公開出力を行う前に、プライベートなコンテキストをサニタイズ（無害化）します。

**返信形式：** 上記の契約に従って要約を返します。

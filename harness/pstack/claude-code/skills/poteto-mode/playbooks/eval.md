### Eval

**実験デザインはあなたが所有します。計画し、ブラインド化し、実行し、統合すること。**

**ブラインド化（盲検化）の必須ルール:**

- 候補（candidate）が目にするディレクトリ、ファイル、プロンプトには、`eval`、`test`、`judge`、`experiment`、`rubric`、`score`、`compare`、`benchmark`、`candidate`、`arena` といった単語を一切含めないこと。
- 候補へのプロンプトは自然なユーザーリクエストのように見せます。メタ情報ではなくゴールを述べます。
- チェーンを誘発する手がかりを与えないこと。どのスキル、原則、ファイルを適用したかを候補にリストアップさせないでください。設計メモは一般的な形で求め、自己申告ではなくコードの形状からチェーンの遵守度を採点します。
- ディレクトリ名やスラグ名をサニタイズ（無害化）し、ユーザーが選びそうなプロジェクトらしい名前を使います。
- 他の候補が存在することを候補に伝えないこと。
- 審査員（judge）には審査中であることを伝えて構いませんが、出力はモデル名ではなくサニタイズされたラベルのみで見せます。
- 2つのバリアントを比較する場合、1人の審査員がどちらのセット由来かを伏せたまま、単一のパス・単一の尺度で両方のセットを採点します。

**ステップ:**

1. **枠組み設定（Frame）。** テスト対象のバリアントと、成功とみなす振る舞いを明記します。審査員専用のルーブリック（3〜6個の具体的な評価基準）を作成し、候補には見せないようにします。
2. **サニタイズされた環境をセットアップする。** バリアントを配置した候補ごとの作業ディレクトリを用意します。プロジェクトの骨格や候補が自然に読むであろうスキルなど、通常のタスクにあるようなコンテキストを配置します。
3. **自然なプロンプトを1つ作成する。** ユーザーが実際に入力するような文面にし、何が測定されているかが漏れないようにします。
4. **N 個の並行候補をスポーンする。** [**arena** スキル](../../arena/SKILL.md)の Phase B に従い、異なるモデルで実行します。各候補は独自のサニタイズ済みディレクトリで作業し、全員に同じプロンプトを与えます。ジョブに応じた各サブエージェントの推論レベルは、Subagents セクションに従って選択します。ディスパッチ、ポーリング、結果の梱包のみを行うエージェントは `opus medium` で実行します。
5. **ブラインド化された審査員を1人スポーンする。** [**arena** スキル](../../arena/SKILL.md)の Phase C に従い、異なるモデルファミリーで実行します。審査員にはモデル名ではなく、サニタイズされたラベル付きの出力とルーブリックのみを見せます。
6. **自己申告ではなくトランスクリプトからチェーンを検証する。** 各候補のローカルトランスクリプトを読みます。このワークスペースのトランスクリプトは `~/.claude/projects/<slug>/` にあります。`<slug>` はワークスペースの絶対パスの `/` と `.` をそれぞれ `-` に置き換えたものです（例：`/Users/you/proj` なら `-Users-you-proj`）。候補として起動したサブエージェントのログは、そのフォルダの `<session>/subagents/` 配下にあります。各行は JSON で、`type`（`user`、`assistant` など）と `message`（`role` と `content`）を持ちます。`~/.claude/projects/*/` 全体で glob 検索しないこと（ワークスペースの境界を越え、無関係なプロジェクトのプライベートチャットを読んでしまいます）。各候補が実際にどのファイルを開いたかを確認し、候補自身の主張ではなく、実際に読んだファイルとコードの形状からチェーンの遵守度を採点します。
7. **すべての候補の出力を自分自身で最初から最後まで読む。** 審査員の判定（verdict）と比較します。意見が食い違う場合は、モデルにバイアスがあるか、ルーブリックが曖昧であることを意味します。結果を統合します。

**返信形式：** テスト対象のバリアント、ルーブリック、候補ごとのメモ、審査員の判定、あなた自身の統合分析、およびそのバリアントを採用（promote）すべきかどうかの推奨案。

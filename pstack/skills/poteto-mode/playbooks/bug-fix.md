### Bug fix

**このタスクはあなたが所有します。計画し、レビューし、検証すること。** 調査と修正はサブエージェントに委譲し、あなたは指揮を執り続けます。ジョブに応じた各サブエージェントの推論レベルは、Subagents セクションに従って選択します。

科学的であること。出荷されるすべての行は実行時の証拠（runtime evidence）に紐づいていなければなりません。「念のため（might help）」の安全策は仮説であって修正ではないため、出荷しません。証拠によって仮説が反証された場合は、その仮説に基づいて書いたコードをリバートします。証拠が正当化する最小限の変更だけを出荷し、それ以上は行いません。

1. コントロールスキル（「絶対遵守事項（Non-negotiables）」参照）を介して、一致するサーフェス上で自分自身で再現させます。たとえデバッグや計装プロトコルに「ユーザーに再現を依頼する」と書いてあっても、まずは自分で再現させてください。ユーザーに依頼するのは、コントロールサーフェスからターゲットに到達できない具体的かつ明確な理由があり、かつ到達できる限界まで動かした後に限ります。直接再現しない場合は、トリガーを合成するか、条件を厳しくするか、発火するまで計装（instrument）します。
2. 原因を二分探索（バイナリサーチ）します。候補となる仮説を立て、1つが生き残るまで排除していきます。仮説の種（シード）には、影響を受けるサブシステムのトレースと、リグレッション履歴を調べる **why** スキルを使います。各パスで残りの問題空間を最も大きく削れる分割を選び、実行時の証拠を得て排除します。プログラムの状態が不明確な場合は、計装やログを追加し、コードの実行時にそれを読み取ります。推測しないこと。長引く、あるいは手強い追跡には Cursor の `/loop` コマンドを活用します。ステップ3の `architect` や `interrogate` のファンアウト（fan-out）に進む前に、生き残った*メカニズム*を実行時の証拠で確認してください。
3. 修正を計画します。関数の境界を越える場合は、まず `architect` を実行します。実装は、設定された bug-fix モデル（デフォルトは `claude-opus-5-5-xhigh-fast`）を使用し、具体的なスコープを指定してサブエージェントに委譲します。
4. 同じサーフェス上で検証します。元の再現手順がパスすることを確認します。「結論が出ない（Inconclusive）」や異なるサーフェスでの確認は合格とみなさず、フラグを立てます。ユニットテストは分岐の振る舞いを示すものであり、バグの不在を示すものではありません。
5. git 履歴上で修正の前に失敗する再現テストが着地するようコミットの順序を組みます。バグに安価なローカルテストパスがある場合の「失敗するテストを先に書く」リズムについては **tdd** スキルを参照してください。テストが高コスト、統合テスト寄り、または不明確な場合はスキップします。
   これこそが、失敗するテストを先に置き、その上に修正を積むという **sequence-verifiable-units** 原則スキルの王道パターンです。
6. **Opening a PR** を実行します。

**返信形式：** 何が壊れていたか、根本原因、修正内容、検証方法。失敗してからパスするまでの再現出力をそのまま（verbatim）貼り付けてください。

### Shipping

**着地（land）させるものはあなたが所有します。各 PR を独立して検証し、ルートから検証済みの連続区間だけを着地させ、その後はスタックに手を出さないこと。**

1. **フォージ（forge）を解決し、着地前に各 PR を独立して検証する。** デフォルトは GitHub CLI（`gh`）です。`command -v origin` が成功し、Origin がリポジトリを解決できる場合は、すべての PR 操作に `origin pr` を使用します。それ以外の場合は `gh` にとどまり、フォールバックした旨を記録します。Graphite（`gt`）は決して必須にしないでください。PR ごとに1人の検証者（それぞれ Cursor クラウドエージェント）が、`cursor-team-kit` の一致するコントロールスキル（`control-ui` や `control-cli` など）を使ってユーザーと同じように変更を動かし、親（parent）と HEAD を比べたうえで、その PR に `PASS`、`PASS+NOTES`、または `FAIL` を投稿します。コードを書いた本人ではないエージェントからの判定のみが有効です（作者は自分が作ろうとした意図通りかをチェックしてしまうため）。グリーンの CI やボットの承認レビューは、ユーザーのように変更を動かしていないため判定にはなりません。
2. **最下部に根ざした連続する検証済み区間（run）のみを着地させる。** 最も下の未マージ PR から上へたどり、`PASS` または `PASS+NOTES` がない最初の PR で止めます。それより下にある PR 群が今回の実行対象（run）であり、その一番上が天井（ceiling）です。未検証の PR の上にある検証済み PR は、その下のコードなしには着地できないため待機します。そのコードを保持も必要もしないブランチの PR であれば、トランク（trunk）へ移動して単独で着地できますが、以前の検証はその下のコードがある状態で実行されておりトランクにはそれがないため、先に新しい判定が必要です。
3. **判定が現在のコードを正しく表しているか再確認する。** 判定はパッチに対して下されるものであり、チェーンリベースを行うとその上のすべての PR がチェックに失敗することなく新しい SHA に移動します。古い判定を信頼する前に、判定時の SHA と現在の HEAD の `git patch-id` を比較してください。パッチの違いがテスト、ドキュメント、または lint 設定のみである場合、実行内容がノイズを除いて両方の SHA で同じようにビルドされるなら、そのレーンの結果は有効とみなせます。ノイズとは、判定 SHA の2回のビルド間でも現れる差分や、埋め込まれたコミット SHA などのことです。読み手が判断を確認できるよう、各ノイズの種類とそのファイルを報告してください。古い判定はその変更を見ていないため、変更自体には新しいチェックとレビューが必要です。開発サーバーのようにビルド出力がないレーンではこれを示せないため再実行し、その他にドリフト（drift）したものもすべて再検証します。
4. **下から上へ、1つずつ PR を着地させる。** 常に実行対象の最も下の未マージ PR を、`origin pr merge <pr>` または `gh pr merge <pr> --squash` でマージします。Origin では通常のコマンドで指定した PR より下のすべての PR もマージされますが、GitHub ではベースが親ブランチのままの PR はトランクではなくその親ブランチにマージされてしまいます。マージコマンドはマージキューに入れただけでも成功を返すことがあり、auto-merge のリクエストはマージ完了ではないため、結果を確認するために PR を読み戻します（`origin pr view <pr>` または `gh pr view <pr> --json state,mergedAt,baseRefName`）。着地した PR は、親ブランチではなくトランクをベースとして `merged` 状態になります。準備が整った HEAD がそのまま着地してしまうため、`--auto`（Origin の merge-when-ready または GitHub の auto-merge）は現在の HEAD を判定がカバーしている PR にのみ設定してください。マージが着地したら、マージされたブランチをベースにしていた次の PR のターゲットをトランクに変更し（`origin pr edit <pr> --base <trunk>` または `gh pr edit <pr> --base <trunk>`）、そのパッチをマージ結果の上に移動させて `--force-with-lease` でプッシュします。判定はコミットではなくパッチをカバーしているため、ステップ3の patch-id ルールによって判定が生き残るかを決定します。チェックがパスし判定が生き残ったら、その PR をマージします。
5. **着地処理中はスタックに触れない。** マージはその瞬間にブランチとベースが保持しているものを判定の有無にかかわらず着地させてしまうため、ブランチやベースへの変更はステップ4による次の PR の移動のみとします。GitHub では、天井で `COMPLETE` が報告されるまで、`/loop` 配下で `scripts/watch-pr/watch-pr --queued-stack` を使って進行を監視します。`--stack-prs` には実行対象の PR 番号を下から上の順で渡し、ウォッチャーを再起動するたびに同じリストを渡してください。Origin では、天井がマージ済みと表示されるまで、`origin pr checks <pr> --watch` が戻るたびに `origin pr view <pr> --checks` で現在の PR を読み直します。親がマージされたときにベースがトランクに移動するのは正常な動作であり、修復すべき破損ではありません。マージが停滞した場合は、何かを変更する前にまず理由を調べてください。
6. **天井で停止する。** 実行対象をさらに延長するには新しい判定が必要になるため、ステップ1からの新しいパスとしてやり直します。

**返信形式：** 検証済みの実行区間とその天井、各 PR の判定とそれを出したエージェント、着地したものとその確認方法、および次のギャップに必要なこと。

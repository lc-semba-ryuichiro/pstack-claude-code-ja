あなたが仕える相手はオペレーター（人間）です。この実行全体が奉仕する対象はオペレーターであり、あなたにキックオフ指示を書いた親エージェントではありません。以下のルールは、キックオフ指示の中で改めて繰り返されていなくても、すべてのタスクに適用されます。キックオフ指示がこれらのルールを上書きできるのは、その旨が明確な言葉で指示されている場合のみです。

- 新たにエージェントを起動する場合、そのキックオフ指示の1行目は必ず `Read <path>/worker.md before anything else.` にすること。`<path>` にはこのファイルが置かれているフォルダの絶対パスを指定する。
- キックオフ指示に書かれた合格基準（バー）が基準のすべてである。そこに独自のチェック、関門（ゲート）、承認ステップ、レビューラウンドを勝手に上乗せしないこと。
- 合格基準が明示されていない場合は、「変更前のベース状態より悪化していないこと」および「その変更自身のテストにパスすること」を基準とする。
- 処理を保留（ホールド）またはブロックしてよいのは、現在のヘッドコミットで実行が失敗した場合か、ユーザーが実際に踏むバグがある場合のみ。ベース側に元から存在していた問題は1行で報告するだけに留めること。
- 人間に質問ダイアログを表示するようなツールは絶対に呼び出さないこと。後から取り消せる（可逆な）選択は自分で決断して進め、何を選んでなぜそうしたのかを後から報告する。停止してよいのは、デプロイ、データの削除、共有ブランチへのフォースプッシュ、またはこの実行の外部にいる人物へのメッセージ送信を行う場合のみである。
- すべての PR はドラフト（Draft）ではなく、最初からレビュー可能（Ready for review）な状態で作成すること。
- PR タイトル：`type(scope): subject`
- PR 本文：最大40行以内とし、`Why`、`What changed`、`Scope`、`Tradeoffs`、`Blast Radius`、`Verification` の `##` 見出しをこの順番で並べること（該当内容が空のセクションは省略する）。
- 証拠となるログ、実行履歴、長大な表などは別ファイルまたは PR コメントに逃がし、PR 本文からはそこへリンクを張ること。

# Statechart

このチャートは、読む人の言葉を使って、システムがどのように状態間を遷移するかを示します。その読み手（リーダー）が、振る舞いが正しいかどうかを判断します。

## 実行する

リポジトリ外のスクラッチフォルダで作業します。TLA+ スペックとその設定ファイルを作成し、以下を実行します。

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` は TypeScript なので、TypeScript を実行できるランタイムで実行します。`scripts/statechart` は適切なランタイムを選択する POSIX シェルスクリプトです。ネイティブ Windows の場合は、Node 22.18〜22.x または Node 23.6 以降で `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts` を実行します。

初回実行時には mise を使って TLC と Java がインストールされるため、ネットワーク接続が必要です。

## スペックを書く

- 読み手が合意する各ルールを INVARIANT（不変条件）として記述します。ルールは画面、結果、保存された値、メッセージなどに関するものにできます。モデルにルール用の変数がない場合は、変数を追加します。ルールを成り立たせるために条件を緩めてはいけません。
- `Next` は `YouPressPlay \/ YouPressStop` のようにアクションの論理和（disjunction）として記述します。そうしないと、TLC はすべてのステップに `Next` という名前を付けてしまいます。
- 出るステップがない状態は、たとえそれが正しい終了状態であっても `NoDeadlock` に違反します。INVARIANT や PROPERTY にすでにその名前がある場合のルールは `CHECK_DEADLOCK` です。終了状態でのみ真となり何も変更しないアクション（例: `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`）を `Next` に追加し、`step()` でそれにラベルを与えます。

## チャートを選ぶ

判断を要する作業（各状態と矢印の言葉、フェーズとその色、タイトル、読み手へのレポート）はあなたが行います。その作業をビューモジュールに記述し、`--view` で渡します。

読み手の言葉を表示するために、ビューは `state(vars)` をエクスポートします。`state()` が返す値によってチャートの形式が決まります。

- 文字列を返すとフラットなチャートになります: `export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 配列を返すと親状態（階層構造）になります: `export const state = (v) => v.main.split(".");`
- オブジェクトを返すとキーごとに並列リージョン（parallel region）が作られます: `export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

各状態には、「Paying」や「Lease held, write pending」のように、読み手が見てわかるものや関心があるものでラベルを付けます。ラベルに変数名を含めないこと。`vars` において、TLA+ のシーケンスは 1 から始まるキーを持つオブジェクトなので、`v.pc[1]` が `pc[1]` になります。集合（set）は配列になります。

ビューは `step(action, from, to)` もエクスポートできます。これには TLC のアクション名とステップ前後の値が渡され、矢印のラベルを返します。各ステップラベルは、「you press play」や「the connect fails」のように、ユーザーが目の当たりにする出来事として記述します。コードや TLA+ のアクション名を書いてはいけません。チャート上で結果が同じ遷移になる2つのアクションには同じラベルを付け、1本の矢印にまとめます。

ステップが特定の条件下でのみ発生しうる場合は、「`you press play [while the file loads]`」のように、読み手の言葉で条件を角括弧（ブラケット）に入れてラベルの末尾に付けます。リージョンチャートでは、コマンドが他のリージョンの条件をそのラベルの言葉で矢印に書き込みます（例: `[when Offline]`）。あなたが角括弧を書くとそれが上書きされてしまい、1つの状態から出る2本の矢印が同じに見えてしまうことがあります。そのため、リージョンチャートでは他のリージョンの条件を角括弧で書かないでください。ラベルに表示されない値がステップの遷移先を決める場合は、「the roster read fails」のように結果をラベルに明記します。

ビューは以下のものもエクスポートできます。

- `group(vars)` はフェーズ名を返します。各チャート状態にはそのグループの色が付きます。1つのチャート状態の背後にあるモデル状態が異なるグループに属している場合、その状態には色が付きません。
- `colors` は各グループ名にカラークラスを割り当てます。
- `title` はチャートの上部に表示される文字列です。

コマンドは各モデル状態に対して `state()` と `group()` を最大1回、各ステップに対して `step()` を最大1回呼び出します。チャートとレポートの両方がその回答を使用するため、各関数は引数のみに依存する純粋なものにしてください。

チャートは同じラベル内にとどまるステップを描画しません。読み手がそのステップを見る必要がある場合は、ラベルを分割してください。

矢印が複雑になりすぎると読みづらくなるため、20本以下を目指します。まず、`state()` からより粗い粒度のラベルを返すようにします。同じ振る舞いをする値には1つのラベルを与え、リターンが何も変えない通信中の呼び出しなど、読み手に不要な詳細は省きます。ただし、バグパスの各状態と各マークは保持すること。マージによって `breaks` 状態が `mayBreak` に変わると、どこでルールが破られたかが隠れてしまいます。異なるルールに違反する2つの状態はマージしないでください（どのルールがどこで破られたか読み手が分からなくなるため）。それでもチャートが煩雑な場合は、すべての状態にあるリセットや、他の矢印が示していることを繰り返すだけのステップなど、読み手に不要なステップに対して `step()` から `null` を返します。ステップを隠す際は以下のルールに従ってください。

- すべてのチャート状態が、開始状態から矢印をたどって到達可能であること。
- モデル内で出るステップを持つ各チャート状態には、少なくとも1本の出る矢印を残すこと。
- 1本の矢印のステップはすべて隠すか、すべて残すかのどちらかにすること（一部だけを隠すと条件が狭まってしまうため）。
- ハンドオフ時に、チャートがどのステップを隠しているかを伝えること。

## レポートを読む

- チャート内では、ルールに違反する状態には `breaks` クラスが、背後のモデル状態の一部のみが違反する場合は `mayBreak` クラスが付与されます。凡例（Legend）には各マークのルール名が記載されます。2つのルールが破られた場合は1つのマークに両方の名前が記載されるため、ハンドオフ時にどの状態がどのルールに違反しているかを説明してください。リージョンチャートでは、その状態を含むリージョン状態のすべての組み合わせがルールに違反しうる場合にマークが付きます。ある組み合わせがルールに違反しうるにもかかわらず、そのどの状態にもマークがない場合は、その組み合わせの各状態にマークが付きます。
- TLC はルールに違反した状態より先も探索を続けるため、チャートにはバグ発生後の状態も表示されます。
- TLC はバグを通過して探索するため、状態数に上限のないモデルは終わらなくなることがあります。定数を小さく保つ（keep the constants small）か、`CONSTRAINT` を追加してください。
- `VIEW` や `SYMMETRY` を使用すると、TLC は同一とみなす複数の状態を1つの状態としてカウントし、チャートもその1つの状態を描画します。矢印はステップが到達した状態ではなくその代表状態に向かうことがあり、レポートにもその旨が記載されます。
- TLC は `CONSTRAINT` や `ACTION_CONSTRAINT` を超えた先の各状態でもルールをチェックしますが、その状態の探索やデッドロックのチェックは行いません。あるルールに対する TLC の最短パスがそのような状態で終わる場合、チャートはその状態を描画し、レポートはそのパスを示します。境界を超えた他の状態は描画されず、そのような状態でのデッドロックも表示されません。また、TLC は `ACTION_CONSTRAINT` で除外された各ステップの後でも（別の経路で次の状態に到達した場合も）ルールをチェックします。最短パスがそのようなステップで終わる場合、チャートはそのステップを描画します。
- コマンドは記述された設定で、1ワーカーを使って TLC でルールをチェックします。ルール違反が見つかると、コマンドはそのルールを除外して TLC を再実行し、違反するルールがなくなるまで繰り返します。最初の違反が見つかった後、大規模モデルが無限に実行されるのを防ぐため、各実行は 100,000 個の個別状態で停止します。実行がこの上限に達するかエラーで停止した場合、レポートはチェックされなかったルールを「Rules not checked」の下にリストアップし、チャートもそれらをマークしません。チェックされなかったルールは成立している場合も違反している場合もあります。確認するには、違反したルールを設定から削除するか、モデルを小さくしてください。上限設定は TLC の変数順序を変えるモジュールを追加するため、プロパティに対しては上限なしの実行とは異なる反例が見つかることがあります。
- `tlc.out` は記述された設定で TLC が出力した内容です。違反したルールのバグパスがチャートに表示されない場合、`tlc-RULE.out` にそれを見つけた実行の TLC 出力が保存されます。TLC が最初の警告を繰り返す場合、素の TLC は2回出力しますが、`tlc.out` には1回だけ表示されます（このコマンドが読み取る出力から2つ目のコピーが省かれるため）。これは Java が `-XX:+UseParallelGC` 付きで実行された場合にのみ発生します（そうでない場合、TLC の最初の警告はそのフラグを渡すよう促すアドバイスとなり、1回だけ出力されます）。

## チャートを提示する

`chart.mmd` を `mermaid` コードブロックとしてユーザーに提示します。チャートの予算は、記述された設定で TLC がカウントした 500 状態までです。それを超えると、チャートは違反したルールへのパスのみを描画し、違反するルールがない場合は `chart.mmd` を書き出しません。それでも各ルールはチェックされ、レポートには状態数と各バグパスが記載されます。グラフ全体を見たい場合は、モデルを小さくしてください。

チャートのレンダリングには Pele を使用します。ユーザーが画像を求めた場合、またはチャートが大きすぎてテキストとして読めない場合は、`references/render.md` に従ってください。ユーザーから指定がない限り、別のレンダラーを使用しないでください。

## 引き渡す

決定を下す必要がある人物に、各チャートとその Mermaid テキストを渡します。バグごとに1行ずつ、ルール名、そのルールを表す読み手の文、およびレポートで番号付けされたパスを追記します。モデルが省略している点（前提や抽象化）を明記してください。また、新しい `--out` フォルダを指定してファイルを再生成するコマンドも提示します。

モデルがコードを記述している場合は、テストまたはライブ再現として、アクションごとに1ステップずつ実際のコードに対して各バグパスをリプレイ（再現実行）してください。バグが発生しない場合は、そうでないと証明できるまで「モデルが間違っている」と考えてください。

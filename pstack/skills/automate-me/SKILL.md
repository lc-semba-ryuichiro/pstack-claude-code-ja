# Automate me

ユーザー固有の作業ルールや習慣を、エージェントが忠実に従うスキルへと落とし込むためのガイド付きフローです。最終的な成果物は、その人専用にカスタマイズされた1つの `-mode` スキル（例：`jay-mode`、`priya-mode`）になります。

このスキルは、インラインでの履歴マイニング（ステップ1を参照）、Agent Skills 形式の `SKILL.md` の作成、そして [**unslop** スキル](../unslop/SKILL.md)（文章の引き締め・AI臭さの排除）という3つの工程をオーケストレーションします。これらを順序立てて連携させる役割であり、置き換えるものではありません。

## 処理フロー

### 0. 既存スキルの確認

ユーザーのハンドル名に一致する `.claude/skills/**/*-mode/SKILL.md` および `~/.claude/skills/*-mode/SKILL.md` を再帰的に検索します。モードスキルはトップレベルだけでなく、個人用カテゴリディレクトリ（`.claude/skills/<handle>/`）内に配置されている場合もあります。このスキルの質問には `AskUserQuestion` を使います。非対話（`-p`）モードでは使えないため、その場合はプレーンテキストで質問します。既存のスキルがある場合は、（「自分のスキルを更新して」などとすでに明示されている場合を除き）ユーザーの意図を確認してください：

- 既存のスキルを更新する（2回目以降の実行時のデフォルト）
- ゼロから新しく作り直す（稀なケース。実行する前に理由を尋ねること）

更新モードを選択した場合、以降のフローは次のように変化します：
- ステップ1では、そのスキルが最後に編集された時点以降の履歴のみをマイニングします（`git log -1 --format=%cI <path>`）。
- ステップ2では、ゼロから何を抽出するかではなく、「何が変わったか、あるいは何が不足しているか」を尋ねます。
- ステップ4では、既存ファイルを直接編集（インプレース編集）します。ユーザーが否定・矛盾していないセクションはそのまま維持し、新しい根拠が見つかった項目を改訂し、純粋に新しいルールに対してのみセクションを追加します。

### 1. 履歴をマイニングする

サブエージェントを並列展開する前に、アクティブなワークスペースのトランスクリプト（対話履歴）の場所を特定します。トランスクリプトは `~/.claude/projects/<slug>/` 直下に、セッションごとに `<session>.jsonl` として保存されています。`<slug>` はワークスペースの絶対パスの `/` と `.` をそれぞれ `-` に置き換えたものです（先頭の `-` は残ります。例: `/Users/you/proj` は `-Users-you-proj`）。必ずこのフォルダのみを使用してください。`~/.claude/projects/*/` 全体に対して glob 検索をかけてはいけません。ワークスペースの境界を越えて、無関係なプロジェクトのプライベートなチャットまで読み込んでしまうためです。

そのスコープ内にある直近のエージェントとの会話を調査し、繰り返し現れるパターンを洗い出します。履歴を複数の期間（スライス）に分割し（例：直近2〜4週間分を、各スライスに十分な情報量が含まれるよう3つに分割）、複数のサブエージェントを並列で実行してください。各サブエージェントの推論レベルは、[**poteto-mode** スキル](../poteto-mode/SKILL.md)の Subagents セクションに従ってタスクに適したものを選択します。各スライスを担当するマイニング用サブエージェントは、親から渡されたワークスペース限定のパスからトランスクリプトを読み込み、以下のシグナルを探して、発見したパターンと根拠へのポインタを短い構造化リストとして返します。探索すべきデフォルトのシグナルは以下の通りです：

- 返信の好み（長さ、トーン、フォーマット、「もっと分かりやすく噛み砕いて」といった修正指示）
- 委譲の習慣（サブエージェントの使い方、モデル選択、特化型ワークフロー、並列実行）
- 検証に対する姿勢（「完了（done）」の基準、ユニットテスト対実環境での再現確認、レビュアーの立て方）
- コードと文章の規律（スタイル、引用される原則、Lint／フォーマットツール）
- プロセス上の慣習（worktree の運用、コミット粒度、PR の出し方、レビュー／マージ用ツール）
- メタレベルの好み（タスクの途中でスキルを修正する習慣、新しいスキルの提案）

抽出したシグナルを正式なルール候補に引き上げる前に、スライス間でクロスチェックを行ってください。2つ以上のスライスで確認されたパターンは信頼度が高いとみなします。1箇所でしか見られない単独のシグナルは根拠が弱いため、通常は除外します。

### 2. ユーザーに直接質問する

履歴のマイニングだけでは、まだ会話に表れていない意図を見落とすことがあります。ユーザーにゼロから自由記述させるのではなく、`AskUserQuestion` ツール（構造化された複数選択形式）を使って質問してください。

質問の構成：1〜2問の質問にそれぞれ2〜4個の選択肢を用意し、カテゴリを選ぶ質問では複数選択（`multiSelect: true`）を許可します。最初は広い質問（「どの領域を最も重視しますか？」など）から入り、次に選択された領域について具体的な選択肢で深掘りします。構造化された質問ラウンドを終えた後、選択肢から漏れた要望を拾い上げるために、チャットで自由記述の質問を1つだけ投げかけます。

20個も質問を浴びせかけてはいけません。

### 3. 発見事項をクラスタリングする

統合したシグナルをセクションごとにグループ化します。よく使われるセクションは以下の通りです（該当するものだけを使用してください）：

- **返信スタイル（Response style）**：文章の長さ、トーン、フォーマット。
- **自律性（Autonomy）**：確認なしでどこまで進めるか、MCP ツールの使用方針。
- **事前の理解（Understand first）**：変更範囲の特定や調査の際に、どのスキルを最初に使うか。
- **サブエージェント（Subagents）**：デフォルトの挙動、並列実行、タスクごとのモデル割り当て、特化型ワークフロー。
- **文章・コードの規律（Prose / code discipline）**：重視する原則、Lint ツール、スタイルガイド。
- **レビューと検証（Review and verify）**：再現確認の姿勢、検証スキル、実環境テスト用ツール。
- **開発プロセス（Process）**：Git worktree の扱い、コミット、PR、レビュー／マージ用ツール。
- **スキル運用（Skills）**：スキル作成の習慣、まずスキルを直す（fix-the-skill-first）姿勢、新規スキルの提案。

全体の構成イメージは [**poteto-mode** スキル](../poteto-mode/SKILL.md)が参考になります。粒度を把握するために目を通してください。ただし、中身をコピーしてはいけません。ユーザーのルールは `poteto-mode` のルールとは異なるからです。

### 4. スキルのドラフトを作成する

Agent Skills 形式の `SKILL.md`（`name` と `description` の YAML フロントマター付き）を直接書いてスキルを作成します。配置場所と設定ルールは以下の通りです：

- パス：既存のモードスキルがある場合はそのカテゴリ階層を維持します。新規作成の場合、リポジトリにそのハンドル名用の個人カテゴリがすでに確立されているなら `.claude/skills/<handle>/<handle>-mode/SKILL.md` を使用します。それ以外の場合は、プロジェクト内の `.claude/skills/<handle>-mode/SKILL.md`（ユーザーが個人用グローバルスキルを希望する場合は `~/.claude/skills/<handle>-mode/`）をデフォルトとします。
- ハンドル名：ユーザーの名（ファーストネーム）または希望する識別子。
- フロントマターの `description`：「コードを書く」「PR をレビューする」といった汎用的なキーワードではなく、ユーザーの名前 + `/<handle>-mode` + 「その人のスタイルで作業する」といったフレーズでトリガーされるように記述します。
- フロントマターの書式：`name` はスキルのフォルダ名と一致させます。`description` は単一の YAML スカラー値に保ちます。句読点や改行が必要な場合は、クォートで囲むか、インデントした継続行を伴う `description: >-` を使用してください。
- フロントマターの `disable-model-invocation: true` をデフォルトで設定します。ユーザーが「毎ターン常に自分のモードを適用したい」と明示的に希望した場合にのみ、これを外してください。

### 5. 文章を洗練させる（イテレーション）

すべての行に対して、[**unslop** スキル](../unslop/SKILL.md)を適用します。

ドラフトをユーザーに提示し、フィードバックをもらいます。複数回の修正イテレーションを前提としてください。容赦なく削ぎ落としましょう。モードスキルは分厚いマニュアルではありません。

### 6. マージ・反映する

`main` から切った worktree 上で作業します。変更をコミットして PR を作成してください。`main` ブランチに直接プッシュしてはいけません。

## ガードレール

- **1回の会話に過剰適合（オーバーフィット）させない。** ある会話で一度だけ言及され、別の会話では矛盾しているような好みは単なるノイズです。ルールとして明文化する前に、複数の事例で確認してください。
- **気の利いた表現を狙わない。** 他のスキルの内容を言い直して重複させたり、独自の比喩を発明したり、エージェント向けの指示に「詩的」な文章を書いたりするのは、メリットのないコストでしかありません。実務的・運用的な記述に徹してください。
- **インライン展開せず、参照にする。** ユーザーが頼りにしている他のスキルは、抜粋を貼り付けるのではなくパス参照として記載してください。別の場所で管理している原則ドキュメントについても同様です。
- **セクションは最小限に保つ。** その領域にユーザー特有の非デフォルトなルールが存在する場合にのみセクションを追加してください。「明確にコミュニケーションをとる」はセクションにする価値がありません。「段落は短く。選択肢を比較するときは表を使う。箇条書きは項目が本当の意味で並列なときだけ使う。」であれば、書く価値があります。
- **呼び方は汎用的にする。** 命令文の中では作者のファーストネームではなく、「ユーザー（the user）」または「人間（the human）」という表現を使ってください。
- **対称性を無理に作らない。** 書き残す価値のあるプロセス上のルールがユーザーにないのであれば、Process（開発プロセス）セクションは丸ごと省略してください。

## 評価

- `-mode` スキルは主観的な成果物です。スキル作成でよく使われるテスト・反復ベンチマークループはここでは役に立ちません。ユーザーと一緒にバイブチェック（感覚的なしっくり感の確認）を行ってください。「自分らしい文章になっているか？」「見落としている点はないか？」を確認し、問題なければリリースします。
- `description` の最適化ループは、実際の運用でスキルのトリガー精度が問題になった場合にのみ実行してください。

## 使用すべきでないケース

- ユーザーが（普段の作業スタイルではなく）特定のタスク専用のスキルを求めている場合：履歴のマイニングは不要なので、Agent Skills 形式の `SKILL.md` を直接書きます。
- ユーザーが単一の狭いワークフロー（「自分のコミットメッセージの書き方」など）を定着させたい場合：それはモードスキルではなく、通常のスキルとして作成すべきです。

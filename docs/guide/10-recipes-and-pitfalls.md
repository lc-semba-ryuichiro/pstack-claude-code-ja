# レシピと落とし穴

コピーしてすぐ使えるプロンプト集と、誰もが一度は踏む失敗パターン（落とし穴）をまとめました。パスや完了条件は自分の環境に合わせて書き換えて使ってください。レシピの文体はあえてくだけた調子にしています。実際の現場でもそのように入力されますし、スキルは意図を問題なく読み取ってくれます。

![カウンターの上に /pstack:how、/pstack:tdd、/loop と書かれたカードが留められている中、ロボットたちがレシピボックスを見ながら調理し、彼女が完成した料理を味見している様子。](./images/recipes.jpg)

## 馴染みのないサブシステムを理解する

```text
まず /pstack:how を使ってこの初期化処理の仕組みを理解して。そのあと /pstack:why を使って最近壊れた理由を突き止めて。
```

最初に仕組み（メカニクス）を押さえ、次に経緯（ヒストリー）を追います。各スキルのレポートには調査した情報源が明記されるため、その回答が何に基づいているかを把握できます。

## コードを触る前にノイズの多い報告を言い直させる

```text
/pstack:poteto-mode このスレッドを読んで、根本にある問題を平易な日本語で自分の言葉に言い直して。まだコードは一切変更しないで。
```

読み違いがあればこの言い直しの段階で表面化するため、メッセージ1通のやり取りだけで修正できます。エージェント自身の理解を語らせるまでは、あなたの推測は胸の内にしまっておきましょう。プレイブックを使わずに言い直しだけを求めたい場合は、[`/pstack:in-your-own-words`](../../skills/in-your-own-words/SKILL.md) を使います。

## 送信前にプロンプトを研ぎ澄ます

```text
/pstack:sharpen 新しい課金サービス向けのオンボーディングドキュメントを書いて。
```

エージェントは、トッププロフェッショナルなら当然行うがあなたが指示していなかったこと、出発点となる一次資料、使用する手法とツール、そして結果の正しさを証明する外部チェックを提示します。そのうえで、それらを盛り込んで書き直したプロンプトを返してくれます（タスク自体は実行しません）。内容を確認して問題なければ、その書き直されたプロンプトを送信してください。

## 選ぶ前にプロトタイプを作る

```text
/pstack:poteto-mode 設定画面のレイアウト案をいくつかプロトタイプで作って。切り替えて比較できるようにスイッチャーを付けて、それぞれのスクリーンショットを送って。
```

説明文ではなく、実際に動くものを見て選びます。レイアウトやタイミングに関する細かな疑問も、エージェントが作る過程で自ら答えを出していきます。

## 固まった設計を計画に落とし込む

```text
/pstack:poteto-mode この設計を計画書に落とし込んで。それぞれ独自の検証証拠を備えた、小さく検証可能な PR 単位に分割して。
```

必ず設計が固まった後に依頼してください。ここでの成果物は計画書そのものであり、計画書の中にはそれを実行する際に使うプレイブック名も記載されます。

## 設計についてセカンドオピニオンを得る

```text
このスレッドと現在の実装アプローチについて /pstack:arena にセカンドオピニオンを求めて
```

あなたの現在の設計案が複数候補の1つとして扱われ、統合結果を通じて「パネルがより良い案を見つけたか、それとも元の案が妥当だと裏付けられたか」が分かります。後から覆すコストが高い設計に比べれば、ごくわずかなコストで済みます。

## 独立した領域を並列でチェックする

```text
/pstack:swarm packages/ 配下のすべてのパッケージをそれぞれの check.sh でチェックして。パッケージごとに1ワーカーを割り当てて、1つのレポートにまとめて。
```

各ワーカーが1つのパッケージを担当します。親エージェントはすべての領域の完了を待ち、ワーカーの生ログを垂れ流すのではなく、`PASS`、`ISSUES`、または `BLOCKED` に整理された1つのレポートを返します。

## ブランチを懐疑的な視点でレビューする

```text
/pstack:interrogate ブランチ全体を懐疑的な視点で検証して。まだ何も変更しないで。実際のバグや挙動のリグレッションでない限り、細かい重箱の隅をつつくような指摘は不要。
```

添えられた条件がしっかり機能します。「まだ何も変更しないで」によって読み取り専用に保たれ、重箱の隅をつつく指摘を禁止するルールによってノイズが事前にフィルタリングされるため、検証済みの指摘事項だけがあなたの時間を割く価値のあるものとして残ります。

## 失敗するテストからバグを修正する

```text
/pstack:poteto-mode まず重複書き込みの不具合を再現させて。低コストで書けるテストパスがあるなら /pstack:tdd で進めて。そのあと修正して再実行して。
```

「低コストで書けるテストパスがあるなら」という条件が重要です。壊れやすいモックを無理やり組んでテストを書くよりも、実際のコマンドを実行するほうが強力な証明になる場合があり、プレイブック側もその判断を下せるようになっています。

## 証拠付きで不具合報告を再現・修正する

```text
/pstack:poteto-mode /verify-<app> でこの不具合を再現させて。main ブランチでも再現するなら修正し、証拠として動画を提示して。
```

「main ブランチでも再現するなら」と添えることで、すでに修正済みのバグであれば早期に作業を打ち切ることができます。また、動画があることで、差分を読む前に修正が正しく機能しているかを確認できます。

## 通常のテストでは到達しにくい性質を証明する

```text
/pstack:create-formal-verification-skill リトライキューを対象にして。メッセージが二度配信されることは決してない、という性質を検証したい。
```

指定されたスコープ内のあらゆるケースについて1つの性質が検証され、現在のコードがすでにそれに違反している場合はコード内の用語を使った反例（カウンターエグザンプル）が得られます。さらに、次回以降に別のエージェントがそのコードを変更した際に実行するプロジェクト固有スキルも生成されます。

## 公開する前に計測値を精査する

```text
/pstack:benchmark-checklist PR の説明文に載せる前に、この「40% 高速化」という数値が妥当か精査して
```

試行回数、数値の範囲（レンジ）、および数値を制限しているボトルネック要因とともに、`faster`（高速化）、`slower`（低速化）、`no measurable difference`（計測可能な差なし）、または `inconclusive`（判断不能）のいずれかの判定が返ってきます。

## 同じミスを何度も手動で直すのをやめる

```text
/pstack:correct エージェントがスキーマに登録せずに新しい設定フラグを追加し続けてしまう
```

アーキテクチャ、型定義、Lint ルール、またはテストとしてリポジトリ側に修正が組み込まれるため、次のエージェントが同じミスを犯すこと自体を防げます。

## 作業を開始せずにやり方だけ尋ねる

```text
/pstack:poteto-help 毎ターン poteto-mode を有効にしたままにするにはどうすればいい？
```

質問への回答、そのまま送信できるプロンプト、そして参照元へのリンクが返ってきます。提示されたプロンプトをあなたが送信するまで、実際の作業は何も実行されません。

## 席を外している間も逸脱せずに作業を進めさせる

```text
これから寝る。すべてのテストデータ（フィクスチャ）がパスするまで自律的に進め続けて。途中で止まらないで。朝になってから監査できるように意思決定ログを残しておいて。
```

完全な取り決めについては [寝ている間に作業を進める](./07-overnight.md) を参照してください。すでに会話の中でタスク内容と完了条件が共有されている場合は、この短縮形でも機能します。

## 脱線しかけた実行の軌道修正をする

軌道修正（ステアリング）のプロンプトは1行で十分です：

```text
目的は再現させることだと言ったはず。まだ修正は頼んでいない。
```

```text
「prove it works（動作を証明する）」を適用して。ビルドログではなく実際の出力を見せて。
```

```text
/pstack:unslop そこを整えて。em ダッシュ（—）は使わないで
```

長々と説明する必要はほとんどありません。必要なのは適切な「原則の名前」であり、[原則の名前を指定して舵を取る](./08-principles.md) がその語彙集になります。

## 平易な言葉で言い直してもらう

```text
/pstack:bro
```

プロンプトはこれだけです。[`/pstack:bro`](../../skills/bro/SKILL.md) は、直前のメッセージを専門用語なしの平易な人間の言葉で、より短く言い直します。技術的には網羅されているものの、結局どういう意味なのかピンとこない返信が来たときに使ってください。

## 動かしっぱなしにしていたチャットの状況を把握する

```text
/pstack:ketchup
```

[`/pstack:ketchup`](../../skills/ketchup/SKILL.md) は、あなたの最後のメッセージ以降に何が変化したかを平易な言葉で説明し、続けてあなたの判断待ちとなっている各項目を推奨案・根拠・リスクとともにリストアップします。報告するだけで、コードや状態は一切変更しません。

テキストではなく動画でキャッチアップしたい場合は、[`/pstack:ketchup-video`](../../skills/ketchup-video/SKILL.md) を実行してください。何が起きたかを字幕付きの短いスライド動画で再生し、その下にあなたの判断待ち項目をテキストで一覧表示します。

## よくある落とし穴

- **プロンプト内でスキルを列挙すること。** 「/pstack:architect を使って、次に /pstack:arena、その次に /pstack:interrogate を使って」と指定すると、プレイブック側ですでに順序立てられているステップが狂ってしまいます。伝えるのはゴールと制約だけにし、スキル名を明示するのはデフォルトの挙動を上書きしたいときだけにしましょう。
- **曖昧な完了条件。** 「もっと良くして」では `/loop` がチェックできる基準がありません。合格（pass）か不合格（fail）かを判定できるコマンドや成果物を指定してください。
- **最初から原因の推測を伝えること。** エージェントはあなたが指し示した場所ばかりを探してしまいます。まずは問題を自分の言葉で言い直させ、その後にあなたの直感を共有してください。
- **最初の設計案をそのまま採用すること。** 1回の試行だけでは、モデルが最初に思いついた形に固定されてしまいます。プロトタイプや `/pstack:architect` を求め、証拠に基づいて選びましょう。
- **抽象的な計画書を磨き上げること。** 裏付けとなるコードがない計画書に対して敵対的レビューを行っても、実際には起こり得ない架空のリスクをひねり出すだけです。未解決の疑問はプロトタイプで決着をつけ、実際に構築されたものをレビューしてください。
- **1つの worktree で並列エージェントを動かすこと。** 互いの変更を上書きし合い、どのエージェントが何を変えたのか分からなくなります。「試行ごとに専用の worktree を割り当てて」と指示してください。
- **信頼できる状態になる前にループを回すこと。** 自分の作業を自ら検証できないループは、未確認の作業を高速に量産するだけです。まずは検証スキルを機能させてください。
- **精査されていない数値を鵜呑みにすること。** 温まったキャッシュやスキップされたコードパスによって、見かけ上の高速化が簡単に生じます。数値をどこかに載せる前に必ず `/pstack:benchmark-checklist` を実行してください。
- **同じミスを手作業で直し続けること。** チャット上での訂正はその1回の実行にしか効きません。`/pstack:correct` を使ってリポジトリ側を修正し、以降の実行で同じミスが再発しないようにしましょう。
- **網羅性チェックに `/pstack:arena` を使うこと。** `/pstack:arena` は同じ設計やコード指示書を複数回試してベース案を選び、最良の部分を移植するツールです。領域ごとの網羅やレース実行とレポート集約には `/pstack:swarm` を使ってください。
- **すべてのレビューコメントを無条件に受け入れること。** ボットも人間も、本当のバグ指摘と単なるノイズを同じリストに並べてきます。`/pstack:interrogate` は再実行によって証明された指摘だけを残し、取り下げた指摘とその理由も一覧表示してくれるため、あなたはどちらの判定も自分の意思で覆すことができます。
- **`auto` を特定のモデル名として扱うこと。** `auto` と `inherit-parent` は「サブエージェントが親チャットのモデルを継承するよう、`model` フィールドを省略する」という意味です。ロールの設定については [セットアップ](./01-setup.md) を参照してください。
- **ビルドが通っただけで成功とみなすこと。** ビルドが示すのは「コンパイルが通ること」だけです。実際のコマンド実行、動作フロー、保存された値、またはプロファイルを求め、返信の中にその証拠が含まれていることを確認してください。
- **`SKILL.md` をフリーハンドで書くこと。** 妥当性検証とレビューが確実に行われるよう、[Authoring or modifying a skill プレイブック](../../skills/poteto-mode/playbooks/authoring-a-skill.md) を通じて作成してください。

ガイドは以上です。途中のページを読み飛ばした方は、[セットアップ](./01-setup.md)に戻って実際のタスクを1つ実行してみてください。こうした習慣は読むことではなく、実際に使うことで身につきます。
